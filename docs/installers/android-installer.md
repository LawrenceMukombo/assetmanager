# Android App — Build Plan

> Status: **Plan only.** No code has been written. Implementation will be scheduled as a separate task once this plan is approved.

## 1. Goal

Produce a distributable Android app (`.apk` for sideload, `.aab` for the Play Store) for NPAMS that the project owner can build from their laptop and hand to ICSA and other agencies. The app must show the existing NPAMS UI and talk to a configurable backend (hosted or LAN).

## 2. Approach Comparison

| | **Capacitor 6** (recommended) | TWA (Trusted Web Activity) | Fresh React Native rewrite |
|---|---|---|---|
| Reuses existing React SPA | Yes (wraps `dist/public` in a WebView) | Yes, but only the *hosted* PWA | No — full rewrite |
| Works offline / on LAN-only | Yes (assets are bundled) | No (requires HTTPS PWA online) | Yes |
| Native APIs (camera, geo) | Yes via Capacitor plugins | Limited | Full native |
| Build output | `.apk`, `.aab` | `.apk`, `.aab` | `.apk`, `.aab` |
| Effort to first build | ~1 day | ~1 day, but needs hosted PWA + asset links | Weeks |
| Risk | WebView quirks on old Android | Strict prerequisites; no offline | High — out of scope per task |

**Recommendation: Capacitor 6.** Rationale:

- NPAMS already builds to a static SPA — Capacitor wraps that exact output in a native Android WebView with one command.
- TWA is rejected because ICSA-style on-prem deployments may run on LAN without public HTTPS, which TWA's Digital Asset Links requires.
- React Native rewrite is explicitly out of scope.
- Capacitor exposes Camera, Geolocation, Filesystem, and Barcode plugins — all needed for asset photos, GIS, and barcode/QR scans.

## 3. Prerequisites on the Build Laptop (Windows / macOS / Linux)

Install once:

1. **Node.js 22 LTS** (matches repo `engines.node`).
2. **pnpm 9+**.
3. **JDK 21** (Temurin recommended — https://adoptium.net). Set `JAVA_HOME`.
4. **Android Studio (Hedgehog or newer)** — https://developer.android.com/studio. During setup install:
   - Android SDK Platform 34 (or current stable).
   - Android SDK Build-Tools 34.x.
   - Android SDK Command-line Tools.
   - Android SDK Platform-Tools (`adb`).
5. **Gradle** — bundled with Android Studio; the project uses the Gradle wrapper.
6. **Environment variables** — set `ANDROID_HOME` (e.g. `C:\Users\<you>\AppData\Local\Android\Sdk`) and add `platform-tools` + `cmdline-tools/latest/bin` to `PATH`.
7. *(Optional, for device testing)* USB drivers for the test phone, or an Android emulator from Android Studio's AVD Manager.

Sanity check:

```bash
node -v        # v22.x
pnpm -v        # 9.x
java -version  # 21.x
adb --version
```

## 5. How Capacitor Wraps the Existing `npams-web` Build

1. `pnpm --filter @workspace/npams-web build` (with `BASE_PATH=./`) produces `artifacts/npams-web/dist/public/`.
2. `cap sync android` copies those files into `android/app/src/main/assets/public/` and refreshes any plugin native code.
3. Gradle compiles the Android shell + bundled assets into `.apk` / `.aab`.

The React app does not need any structural changes for the basic case. Only the API base URL handling needs a small shim (see §6).

## 6. API Base URL Configuration per Environment

The packaged app must talk to a backend that is *not* bundled. Strategy:

1. **Build-time default per flavor**: define `VITE_API_BASE_URL` in `.env.android.production` (e.g. `https://npams.example.gov.lk/api`).
2. **Runtime override**: a Capacitor Preferences key `npams.apiBaseUrl` lets a sysadmin point a fresh install at a LAN server. Read it on app boot via `@capacitor/preferences` and inject into `window.__NPAMS_CONFIG__`.
3. **First-run setup screen**: if neither build-time nor stored value is set, show a "Server URL" dialog before the React app boots.
4. **Cleartext HTTP for LAN deployments**: ICSA on-prem may use plain `http://10.x.x.x:5000`. Add `android:usesCleartextTraffic="true"` to `AndroidManifest.xml` and a `network_security_config.xml` whitelist limited to known LAN ranges.

The React app's API client (`@workspace/api-client-react`) gets the same shim used by the desktop build: prefer `window.__NPAMS_CONFIG__.apiBaseUrl` over the build-time env var.

## 7. Permissions

Declared in `android/app/src/main/AndroidManifest.xml`:

| Permission | Reason |
|---|---|

| `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION` | GIS asset location capture. |
| `READ_MEDIA_IMAGES` (Android 13+) | Pick existing photos for asset records. |

Capacitor plugins to add:

- `@capacitor/camera`
- `@capacitor/geolocation`
- `@capacitor/preferences`
- `@capacitor/network`
- `@capacitor-mlkit/barcode-scanning` (or `@capacitor-community/barcode-scanner`) for QR/barcode

Runtime permission requests are handled by the plugins on first use. The React UI must show a friendly "this app needs camera access" prompt before triggering the request.

## 8. Debug vs Release Builds

**Debug build** — for testing on the owner's phone:

```bash
pnpm --filter @workspace/npams-mobile build:apk:debug
adb install android/app/build/outputs/apk/debug/app-debug.apk
```

The debug APK is auto-signed with Android's debug keystore. Not suitable for distribution.

**Release build** — for ICSA / Play Store:

1. Generate a keystore (one-time, see §9).
2. Configure signing in `android/app/build.gradle` (`signingConfigs.release`).
3. Run `pnpm --filter @workspace/npams-mobile build:apk:release` (sideload) or `build:aab:release` (Play Store).

## 9. Keystore Generation and Signing

One-time on the build laptop:

```bash
keytool -genkeypair -v \
  -keystore ~/keystores/npams-release.jks \
  -alias npams \
  -keyalg RSA -keysize 4096 -validity 10000
```

Store keystore + passwords **outside** the repo (e.g. `~/keystores/`, password manager). Losing them means losing the ability to publish updates.

Reference them from `android/app/build.gradle`:

```gradle
signingConfigs {
  release {
    storeFile file(System.getenv("NPAMS_KEYSTORE") ?: "../../../keystores/npams-release.jks")
    storePassword System.getenv("NPAMS_KEYSTORE_PASSWORD")
    keyAlias "npams"
    keyPassword System.getenv("NPAMS_KEY_PASSWORD")
  }
}
buildTypes {
  release { signingConfig signingConfigs.release; minifyEnabled true; shrinkResources true }
}
```

## 12. Distribution

| Channel | Use case | Notes |
|---|---|---|
| **Direct APK sideload** | ICSA pilot, internal testing | Email/USB the `.apk`. User must enable "Install unknown apps" for the source app. |
| **Internal MDM** (e.g. Microsoft Intune, Google MDM) | Government fleet rollout | Distribute the signed `.apk` via MDM; no user install prompt. |
| **Google Play — Internal Testing track** | QA on real devices | Upload `.aab`, invite testers by email. Fast, no public review. |
| **Google Play — Production** | Public release | Upload `.aab`, complete data-safety + content-rating forms. Requires Play Console account ($25 one-time). |

## 14. Update Strategy

- **Sideload distribution**: send the new `.apk`; user installs over the previous version (same package id + signing key = silent in-place upgrade).
- **Play Store**: upload the new `.aab`; users update via Play.
- **In-app update prompt** (later): use `@capawesome/capacitor-app-update` to nudge users when a newer version is available on the configured channel.

## 15. Risks & Open Questions

- **Cleartext HTTP**: required for LAN ICSA deployments but flagged by Play protections. Mitigation: ship two flavors (`lan` allows cleartext, `play` does not), or always proxy through HTTPS (Caddy/nginx on the LAN server).
- **Old Android versions**: target Android 14 (SDK 34), minimum Android 7 (SDK 24). WebView quirks on Android 7–8 may need testing.
- **Backend CORS**: the WebView origin is `https://localhost` (Capacitor's default scheme) — `cors()` in `artifacts/api-server/src/app.ts` already allows all origins, but production should tighten this.
- **Large WebView bundle size**: NPAMS SPA is ~few MB; Capacitor adds ~3 MB shell. APK should land under 15 MB.
